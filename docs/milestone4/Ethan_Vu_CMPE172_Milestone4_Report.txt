1. OVERVIEW

Milestone 4 adds enterprise AI to the existing HPC reservation application. The
system continues to use Java 21, Spring Security, handwritten JDBC SQL, and SQLite.
Spring Boot was updated to 3.5.7 to use Spring AI 1.1.8. The AI integration uses the
Gemini Developer API with a Google AI Studio key supplied through an environment
variable. The application does not configure Vertex AI project-id or location.

The implementation adds two agents. The conversational agent helps a signed-in
customer find resource availability, list reservations, and propose a booking or
cancellation. The autonomous agent runs on a schedule, generates a personalized
reservation reminder with the LLM, and sends it through the existing notification
gateway. Policy questions are grounded with vector retrieval from a small,
handwritten FAQ dataset. Multilingual chat is the selected bonus feature.

All resources and notifications are simulated. The notification endpoint accepts
messages but does not deliver real email or SMS. The AI does not provision real
HPC nodes or submit actual cluster jobs.

2. CONFIGURATION AND EXTERNAL SERVICE BOUNDARY

The Maven project imports the Spring AI BOM and includes the Google GenAI chat
starter, the Google GenAI embedding starter, and the vector-store module. The
normal scheduler starts without AI credentials. AI functionality is activated
through the ai Spring profile and GEMINI_API_KEY. AI endpoints return HTTP 503
when AI is disabled, while the existing reservation functionality remains usable.

application-ai.properties configures the key through ${GEMINI_API_KEY}. Neither
source code nor this report contains the actual key. Local .env files are ignored
by Git. Docker Compose passes environment variables to the application, and a
local Maven run reads variables from the shell.

The chat model defaults to gemini-4-hydrogen, selected from the current official
Gemini model documentation. GEMINI_MODEL allows an available model to be selected
without changing source code. The embedding model defaults to gemini-embedding-001,
which remains available for text embeddings. GEMINI_EMBEDDING_MODEL can override
that selection. Access and rate limits depend on the API key and Google's quotas.
Thought inclusion is disabled so normal replies contain user-facing output.

The application sends chat messages, retrieved policy text, and tool results
needed for the conversation to Gemini. Users should use non-sensitive demo data.
The reminder generator receives the service and project name; recipient email is
used by the notification gateway, not included in the reminder-generation prompt.

3. AGENT 1: CONVERSATIONAL SCHEDULING AGENT

AiController exposes POST /api/ai/chat. It validates a message of at most 2,000
characters and obtains HpcUser from the authenticated Spring Security principal.
ConversationalAgent uses Spring AI ChatClient and registers a new SchedulingTools
instance for the current customer on each turn. Model arguments cannot select a
different customer ID or grant provider permissions.

The available tools are:

- catalog: reads the actual services, provider IDs, current date and time zone
  through CatalogService.
- checkAvailability: calls SlotService to return future available slots in
  chronological order, with optional date and service filters and pagination.
- listMyAppointments: calls BookingService.list for the authenticated customer.
- book: validates the requested project details and prepares a booking proposal
  from a real available slot; it does not commit a reservation.
- cancel: checks the customer's ownership and prepares a cancellation proposal
  for a future booked reservation; it does not immediately cancel it.

The prompt tells the agent to clarify ambiguity, collect a project name, use real
IDs from the tools, and offer actual alternatives if a requested slot is taken.
For an earliest-slot request, it can read the catalog and then check availability
in chronological order. Spring AI handles tool execution within the model's
conversation loop, allowing multiple tool calls during one customer request.

AiConversation retains the latest 20 user/assistant messages in the HTTP session.
The next turn includes that history, allowing follow-up questions. Tool exchange
internals are not stored as conversation history. Reset and logout clear the
conversation. History expires with the session and is not durable across restarts.

The UI adds an AI Assistant page for customers. It displays model output as text,
shows retrieved policy source IDs, and renders a separate proposal summary from
server data. The browser never inserts generated text as executable HTML.

CONFIRM-BEFORE-WRITE AND TRANSACTION SAFETY

Confirm-before-write is enforced by Java code. A book or cancel tool call stores
a pending action with a random token and a five-minute expiration. The proposal
summary includes the exact reservation or slot, service, provider, start/end time,
project, resource requirements, and account email. A proposal does not hold a slot.

The model receives the proposed summary but never receives the confirmation token.
There is no model-callable confirmation tool. The user must review the server
summary and press Confirm booking or Confirm cancellation. That action calls the
separate POST /api/ai/confirm endpoint with the token and the session CSRF header.
Typing "yes" in chat does not directly commit a reservation.

SchedulingTools.confirm checks that the token belongs to the pending action in
the current customer's session, is unexpired, and has not already been consumed.
It consumes the action before executing it. Every new chat message invalidates
the old proposal. Access within one session is serialized to prevent concurrent
requests from reusing the pending token.

A confirmed booking calls the existing BookingService.book, which delegates to
BookingTransactionService inside the existing SERIALIZABLE transaction and retry
boundary. The conditional slot-version update and appointment insertion commit
together. The partial unique index also rejects a second active appointment for
the same slot. A stale or occupied slot produces HTTP 409. The user can then ask
for fresh alternatives. Notifications occur after the booking transaction commits.

Confirmed cancellation calls BookingService.cancel. Existing ownership and
future-start checks still apply. Customer AI routes require the CUSTOMER role;
provider accounts cannot use customer write tools. All modifying AI endpoints
retain CSRF protection. The tool constructor independently checks customer role
and that the authenticated ID matches the conversation owner.

4. AGENT 2: AUTONOMOUS REMINDER AGENT

ReminderAgent is a Spring service active under the ai profile. Its @Scheduled
method starts after one minute and runs every five minutes by default. It acts
without a user chat prompt. Scheduling intervals are configurable properties.

Each sweep selects at most 100 BOOKED appointments starting within the next
24 hours that have no accepted reminder receipt. For each appointment, it asks
Gemini for a short project-specific preparation sentence. The generated text is
checked for a nonempty, bounded length. Java adds the authoritative reservation
ID, start time, and configured time zone instead of relying on generated facts.

After generation, the agent reads the appointment again. If it has been cancelled
or already started, the send is skipped. Otherwise the agent calls the existing
NotificationClient with type REMINDER, the account contact email, generated
message, appointment ID, and stable appointment-{id}-REMINDER idempotency key.

An accepted send records the appointment ID in SQLite's ai_reminder_receipts
table. This survives application restarts and prevents routine repeat generation
and delivery. If generation fails or the gateway rejects delivery, the appointment
is not marked sent and remains eligible for a later sweep while still upcoming.
One failed reminder does not prevent processing the other selected appointments.
Logging includes appointment IDs and aggregate scanned/sent/failed counts without
recording the generated message or recipient email.

POST /api/ai/reminders/run provides the manual demonstration trigger. It requires
PROVIDER_ADMIN and CSRF protection. A manual run only scans that signed-in
provider's appointments. The internal scheduled run scans all providers. The
provider's Manage Availability page includes a Run AI reminders now button.

This is a real LLM-and-outbound-action task, rather than a job that only logs a
message. Its outbound action uses the project's simulated notification service.

5. GROUNDED POLICY QUESTIONS WITH RAG

src/main/resources/knowledge/hpc-policy.txt contains six synthetic FAQ sections:
hours/time zone, services, booking rules, cancellation, acceptable use/privacy,
and reminder/failure behavior. Each section has an HPC-DEMO source ID. The file
explicitly states that these are teaching-demo policies, not official SJSU rules.

PolicyKnowledge loads this file on the first chat request, splits it into the six
sections, and sends them through the Gemini embedding model. The resulting
vectors and source metadata are stored in Spring AI SimpleVectorStore. The store
is in memory and reingests after restart; it does not require a Chroma container.

For each user message, similarity search retrieves up to three sections using a
minimum cosine similarity of 0.3. ConversationalAgent adds the retrieved text to
the system context. It instructs Gemini to answer policy questions only from that
evidence, cite source IDs, and acknowledge when evidence is insufficient.

The API separately returns the retrieved source IDs so the UI can show what was
retrieved even if the model omits a citation. These IDs identify evidence supplied
to the model; they do not automatically prove that every generated statement is
correct. Live availability and ownership come from service-layer tools, not FAQ
text. User text and retrieved content are treated as data rather than authority
to override tool permissions or confirmation requirements.

6. BONUS: MULTILINGUAL RESPONSES

The assistant is instructed to respond in the user's language or the language
explicitly requested in the conversation. The UI suggests English, Vietnamese,
and Spanish. This lets a customer ask scheduling or policy questions in a familiar
language while the underlying service calls, ownership rules, confirmation UI,
and transactional protections remain unchanged. The deterministic tests verify
that the multilingual instruction and prior conversation enter the model prompt.
Language quality still depends on the live model; automated doubles do not prove
translation accuracy. A live Spanish policy response was also verified during
the smoke test. The interface labels themselves remain in English.

8. DESIGN TRADE-OFFS AND LIMITATIONS

The strongest safety boundary is deterministic confirmation followed by the
existing transactional service. A prompt alone cannot bypass that boundary.
Using the existing service and notification layers also avoids a separate set of
booking rules inside the AI integration.

SimpleVectorStore keeps setup small for this dataset, at the cost of reembedding
after restart. Session history supports multi-turn chat but is not persistent.
Model responses, tool selection, translations, and citations remain probabilistic.
An unavailable or rate-limited AI service returns a safe error; customers can use
the standard reservation screens instead.

Reminder execution assumes one application instance. Its synchronized sweep
prevents overlapping local runs, but it is not a distributed lock. A crash after
gateway acceptance but before receipt insertion can cause a retry. The stable
idempotency key helps, but the mock gateway's deduplication memory resets on
restart. A cancellation can still race the final send after the status recheck.
Failed confirmation/cancellation notifications retain the earlier gateway's
bounded retry/fallback behavior; this work does not claim a general outbox queue.
